# History

How Tessera reached its current form, on October 28 and 29, 2026, with tests run on a Bluefin system with real tokens. The problems are listed in the order they appeared. Each one has the symptom, the cause and the fix.

## The idea (October 28)

1. **The proposal to FlatPark.** A feature suggestion (not a bug report) to FlatPark, which already packages PJeOffice Pro: offer as a Flatpak what distrobox-adv-br offers in a container, that is, SafeSign, SafeNet and SerproID, plus webpki and websigner, usable in Papers and Firefox, for immutable systems.
2. **The maintainer's reply** proposed a "hub" app, in the style of `org.flatpark.Cellar`, with two layers: access to the tokens and, on top of it, the *native messaging* of the web signers. Decision: start with token access, because webpki and websigner are being phased out and are not worth the effort.
3. **The design.** A standalone app, with its own icon, generic (not only ICP-Brasil), with the drivers as extensions. OpenSC stays on the host, which already has it. The chosen name was **Tessera**, the Roman token that identified its bearer. The interface is in Rust with GTK 4 and libadwaita, and the repository is `pedrohqb/tessera`, maintained by the author. The "cleanups" from distrobox-adv-br (no install scripts, no `/etc`, `libneoidp11.so`, the SerproID certificates folder) are the rule for unpacking the drivers.
4. **First builds.** OpenSC needed `winscard.h`, so pcsc-lite was added to the package (the runtime does not ship the client library). Then came folder fixes (`--libdir=lib`, OpenSC's module and *completions* in `/app`) and a meson option that does not exist. Later OpenSC was dropped from the package: the host's copy is served through the same path.

## First tests on the real system (October 29, morning)

5. **Installation failed** with "Dados extras faltando nos metadados destacados" (Flatpak in Portuguese; in English, "Extra data missing in detached metadata"). A standalone `.flatpak` bundle does not carry the extra-data. The test build became a packaged Flatpak repository (`tessera-repo.tar.gz`), with a script that adds it as a local repository.
6. **`bwrap: Can't mount on symlink destination /run/user/1000/p11-kit`.** The first design served the tokens at p11-kit's default address, but Flatpak takes that address for its own trust server. The sockets moved to `xdg-run/tessera`.
7. **Firefox saw p11-kit, but not the token.** p11-kit's user configuration is ignored in every sandbox (`user-config: none`). Hence the current architecture: one server per driver and `remote:` files in `~/.config/pkcs11/modules`, served by the host's `p11-kit-server.socket`. An earlier recommendation, to turn that socket off, was reversed.
8. **SafeSign with no token detected.** `libaetpkss.so` did not load because `libgdbm_compat.so.4` was missing, and the "failed to fork for accept" message came from that failure. The fix was the GDBM packages from Ubuntu 24.04. Token Administration needed wxWidgets, which now comes from the RHEL 10 RPM, as in the AUR package.
9. **SerproID would not open.** The app's script did `cd /usr/share/…`, and the paths were rewritten during unpacking. Then came `Unable to open DISPLAY` (JavaFX), fixed with `--socket=x11`. Finally, the `~/.config/serproid/certificados` folder has to exist, as distrobox-adv-br already did.
10. **"Não foi possível adicionar módulo" in Firefox.** SafeNet, with no token, hung, and a hung driver published on the host hangs whatever loads p11-kit. This led to supervision (only what responds is published) and the per-driver switch.
11. **SafeSign worked in Firefox:** CERTIFICADO OAB, "Logado".
12. **SerproID: `CKR_DEVICE_ERROR` through p11-kit, but working directly.** A server started by hand with `P11_KIT_DEBUG` showed `undefined symbol: _Unwind_Resume_or_Rethrow`. Fix: `LD_PRELOAD=libgcc_s.so.1`. The token fields came with NUL bytes, and they are now cleaned.
13. **Orphan processes.** An orphaned server held on to the socket, and hung connections outlived the server. Fix: `PR_SET_PDEATHSIG` and one process group per server. `p11-kit server` with `P11_KIT_PRIVATEDIR` answered "'server' is not a valid command", so Tessera now runs the `p11-kit-server` helper directly.

## The SerproID login (October 29, afternoon)

The certificate showed up in Tessera and in Firefox, but login failed: the request reached the phone (Application "Tessera"), approving it with Face ID gave "Ops! Estamos enfrentando problemas", the request repeated, and the log showed `Retornando CKR_FUNCTION_CANCELED depois de receber 20 vezes AGUARDANDO`. In the distrobox, the same certificate worked. The cause took an afternoon to surface, because every hypothesis looked plausible:

14. **The "allow-list of apps" hypothesis.** The process that loaded the driver was `p11-kit-remote`, and Tessera started handling the connections itself (`tessera remote`). It did not help. A test with a copy of Tessera named `firefox-esr` also failed.
15. **The "it's p11-kit" hypothesis.** `probe-sign` signed in 4.5 s directly and through both p11-kit hops. That seemed to clear the path, but `probe-sign` asks for the size before signing, and that is a different code path in the driver (item 18).
16. **The "instances knocking each other down" and "stale connection" hypotheses.** There was only one SerproID instance, and a new connection changed nothing.
17. **The host p11-kit's log** (`log-calls: yes`) showed that Firefox requested exactly the same `CKM_RSA_PKCS_PSS` as the tests. Differences: a read-only session and a single `C_Sign`, with no size query.
18. **The size query.** With it, the signature went through, and Tessera started doing it on its own. Login then completed, but the site replied `SSL_ERROR_DECRYPT_ERROR_ALERT`. `sign-test.py`, which checks each signature, showed "PKCS#1 v1.5 of the data as given (NOT PSS)": on that path SerproID ignores PSS. The change was reverted.
19. **Direct tests, one at a time** (all approved with Face ID): direct works; direct with `CKF_OS_LOCKING_OK` works; with p11-kit's command line, with output to a *pipe*, with a new program name and with p11-kit's call sequence (`mimic`), it also works. Through p11-kit, with the original `p11-kit-remote`, with `tessera remote`, with signals restored, with standard input and output swapped and without the managed layer, it always fails.
20. **`strace` and the `getenv` spy:** in both cases, the driver reads the same files, queries the same variables and opens the same connections. But the signing request sent to the cloud was **467 bytes directly and 451 through p11-kit**. So the content was changing.
21. **The cause.** With the PSS parameters wiped right after `C_SignInit` (`sign-test.py clobber`), the direct driver failed immediately. That is, SerproID keeps the mechanism pointer and only reads the parameters in `C_Sign`. Through p11-kit, the memory has already been reused by then. A fake driver with the same defect showed the hash arriving as `0xd963a0444bf2382c` instead of `0x250`. **Fix:** `tessera remote` hands the driver a stable copy of the mechanism.
22. **Login approved:** "Tudo Certo! seu certificado … foi validado com sucesso", at 16:32.

## The other apps and the window (October 29, late afternoon)

23. **PJeOffice Pro:** signing with SerproID with no configuration at all.
24. **Papers showed each certificate twice.** Papers' NSS loads the root module on its own, which in the runtime is p11-kit and, with the `override`, reaches the host server. Together with the registered `p11-kit-client.so`, that made two paths. Fix: a separate, empty NSS database. A Flatseal *reset* wiped the `override` in the middle of the test and showed that it is needed.
25. **Set up did nothing.** It required every driver to be running, and a SafeSign with no token was enough to block it.
26. **SafeSign switched off in the window and Restart having no effect.** A listing started before the restart finished after it and switched off the new driver. Also, supervision only ran with the window open: with the window closed or at autostart, nothing was published. Supervision moved to the service, with generations, three attempts before stopping, and each driver's state on its row.
27. **The window lost its reference to itself,** and results did not reach the screen. When reopened, it showed a window that had already been destroyed. Both defects showed up in a test of the window with Xvfb and xdotool.
28. **Additions:** the tray, the status in the Background portal, removing the modules on quit, automatic Firefox Set up (all profiles), the state of step 1 and of the host server, Chromium, Chrome and Brave, errors in a dialog box, and the new icon (a tessera hospitalis in patinated bronze).

## Clean test (October 29, 2026, evening)

29. **PJeOffice stopped seeing the tokens.** The *reset* had turned off `p11-kit-server.socket`, and the "System connection" row said "On". With the host server off, Flatpak's own trust server answers at the same socket path, and the check only tried to connect. The row now checks end to end: it lists the tokens through the socket and looks for Tessera's.
30. **Firefox said "Close Firefox first" while it was closed.** Tessera looked at the `lock` link, which is left behind when Firefox closes badly. The real lock is an `fcntl` on `.parentlock`, and that is what Tessera checks now.
31. **Chrome, Edge and Brave "with no certificate database".** Since Chromium 146, the NSS database lives in `$XDG_DATA_HOME/pki/nssdb` (in a Flatpak, `~/.var/app/<browser>/data/pki/nssdb`), and no longer in `~/.pki/nssdb`, which only wins if it already exists. Tessera only looked for the old one. With this, the `--persist=.pki` that the window suggested for Chrome is no longer needed.
32. **The SafeSign PIN asked twice in Chrome, Edge and Brave, and three times in Chromium.** Chromium loads the runtime's root module on its own, which is p11-kit and reaches the host server. With `p11-kit-client.so` registered as well, each token showed up twice. Same cause as Papers; the browsers' Set up now only removes the registration.
33. **The SerproID notification with a broken image.** The driver calls `notify-send` with an image from its own folder, which the desktop outside the sandbox cannot open. Tessera puts first in the drivers' `PATH` a `notify-send` that swaps the icon for Tessera's.
34. **Window adjustments:** the steps with the same names in every app ("Step 1 · access to the system's p11-kit server", "Step 2 · certificate database"), no button when there is nothing to do, and updated without restarting Tessera; each app's icon; the tray icon whenever the service runs, with a menu option to hide it.
35. **Chromium still asked for the PIN twice.** The real `~/.pki/nssdb`, which Chromium uses instead of the new database, registered `libnssckbi.so` ("Mozilla Root Certs") by hand, on top of the one Chromium loads on its own. Without that registration, the PIN was asked once. With this, Chromium, Chrome, Edge, Brave and Okular were tested with a real token.
36. **The SerproID notification did not show on Plasma the second time.** Signing twice in a row through Tessera, the second "approve on your phone" went straight to the history; SerproID installed on the host showed it every time. Adding the time to the text did not help. The cause is in libnotify: in a sandbox, `notify-send` goes through Flatpak's notification portal and names each notification after a counter that starts at 1 in every process, so every call was Tessera's notification "1", replacing the previous one. GNOME shows a replaced notification again; Plasma only updates it. Tessera's `notify-send` now calls the portal itself, with a new ID each time.
37. **No `p11-kit-server.socket` on Debian and Ubuntu.** `systemctl --user enable --now p11-kit-server.socket` said the unit did not exist on Ubuntu. Their `p11-kit` package (checked in Ubuntu 24.04 and 25.10, whose packaging is Debian's plus IBM and build patches) ships the server but no systemd units, and builds it without libsystemd, so it cannot take a socket from systemd either. On those systems the README, and the window's copy button, give a plain user service that starts `p11-kit server` at login on the same socket path. openSUSE keeps the units in `p11-kit-server`, which Flatpak only recommends, so the README now names it.
38. **Signing failed on MX Linux (Debian 13).** Tokens, certificates and the PIN worked, but every signature failed at once, in the native Firefox and in Brave (Flatpak), with SafeSign and with SerproID: `SSL_ERROR_HANDSHAKE_FAILED` in the browser, `CKR 0x71` (SafeSign) and `CKR 0x63` (SerproID) from `sign-test.py` through the system's `p11-kit-proxy.so` and through its server. The cause is in p11-kit's RPC: since 0.25.6, a mechanism is sent with a byte saying whether parameters follow, and that is not tied to the negotiated protocol version (0.25.5 and older speak version 1, 0.25.6 and later version 2), so the two sides disagree whenever one is older. Debian 13 has 0.25.5; Tessera serves through the GNOME runtime's p11-kit, which is newer. Listing tokens and logging in carry no mechanism parameters, so they work; the RSA-PSS signature of TLS 1.3 carries them, Tessera's side reads the old layout's first byte as "no parameters", and the driver gets garbage. By package version, Debian 12 (0.24.1), LMDE 6 and 7, Ubuntu 24.04 (0.25.3) and Linux Mint 22 are in the same case; Ubuntu 26.04 (0.26.2) is not. Fixing it in Tessera would mean shipping a patched p11-kit; the decision was not to, and to point those systems to distrobox-adv-br. The window shows a banner on them, with a button to the README's list of distributions, and `tessera status` a warning; Tessera tells them by the protocol version the system's p11-kit server answers in its handshake (1 up to 0.25.5, 2 from 0.25.6 on; Ubuntu 24.04's 0.25.3 answers 1), read once that server is seen serving Tessera's tokens, so the banner follows the system's real p11-kit and goes away when it is updated; while the server is off, by the release codename in `os-release` (`VERSION_CODENAME`, or `UBUNTU_CODENAME` and `DEBIAN_CODENAME` in derivatives such as Mint, LMDE and Pop!_OS). MX Linux then backported p11-kit 0.26.x to its test repository on request, and signing works with it on MX 25: the confirmation that the system's p11-kit version was the whole cause.
39. **More apps: Thunderbird, Evolution, LibreOffice, JSignPdf, Master PDF Editor and Assinador SERPRO.** Each one finds its PKCS#11 modules in its own way, so each got its own recipe, from its source code and its Flatpak manifest (details in [Apps](apps.md)). Thunderbird is Firefox's case, with the module in every profile; its Flatpak changed IDs in 2026 (`org.mozilla.thunderbird`, `org.mozilla.thunderbird_esr`), and the old one still shows when installed. Evolution is Chromium's case: in the runtime, the roots module it adds is p11-kit, so step 1 is enough, and natively it shares the browsers' `~/.pki/nssdb`. LibreOffice picks Thunderbird's or an old-style Firefox profile, or a temporary database, unless a certificate path is set, so Tessera sets one (`CertDir`): an empty database for the Flatpak, one with `p11-kit-proxy.so` for the native app. JSignPdf's Java PKCS#11 opens one slot, by default the first, which on the system's p11-kit server is the trust store: Tessera writes the position of its tokens' slot (`slotListIndex`), and the button stays to write it again. Master PDF Editor takes one library in its settings, under a key not known, so step 2 is by hand. Assinador SERPRO, now on FlatPark, already does what PJeOffice does. None of them has been tried with a real token yet.
40. **OpenSC, built in.** The first design left OpenSC to the host (item 4), but most systems outside the Fedora family do not have it, and the ePass2003 needs it. Being free software, it is now built into Tessera from its release tarball, and served whole, every card it knows, as one more driver; its command-line tools run through `tessera opensc`. Two things came with it. Duplicates: OpenSC's `idprime` driver knows SafeNet's cards, so while SafeNet is on OpenSC gets a configuration without it (`[when_on]` in `driver.toml`); and the window now warns about a token served by two drivers (by the holder's certificate) or seen twice by the apps through the system's p11-kit server, as with Fedora's own OpenSC. And a hang: OpenSC with no reader lists no slot, and the `cryptoki` crate then asked again, with an empty buffer, without end, because p11-kit's RPC answers `CKR_BUFFER_TOO_SMALL` to it; the listing hit its time limit and supervision would have stopped the driver. Tessera now asks for the count first.
41. **The vendors' drivers as extensions.** FlatPark started hosting Flatpak extensions with extra-data, and the first one was a Tessera driver from someone else (Certisign's RemoteID, by its developer), through the extension point Tessera had declared from the start (item 3). Shipping SafeSign, SafeNet and SerproID inside Tessera had meant about 186 MB from four vendor hosts for every user, most of whom need one driver of 2 to 91 MB; any one of those files changing at its URL broke the install and every update of Tessera, and every new vendor version meant a new Tessera. Each is now an extension of its own (`flatpak/extensions`), installed by hand: automatic download was considered and dropped, because it would list three entries on FlatPark that nobody chooses, and drivers from other countries' vendors will come the same way, picked by who needs them. OpenSC stays built in. To make the choice easy, the window lists the missing drivers with their install command, and a token whose driver is missing is recognized by its reader's name or ATR (`src/catalog.rs`). Driver ids became lowercase, since an extension's folder is `SafeNet`. The icons: SafeSign's and SerproID's are the vendors' own; SafeNet's Linux package has only a 32 px badge, so its extension got an icon of its own instead of an enlarged one.
42. **OpenSC and GD Burti.** Testing the extensions, the GD Burti token hung with Tessera's OpenSC on, as it had on Fedora years before with the system's: OpenSC has no driver for the G+D StarSign CUT S, probes it with its card drivers' selects and polls, and the token stops answering, SafeSign included (the token's applet refuses the basic channel, and polling is known to shut it down). Switching OpenSC off fixed it at once. Rather than telling everyone with SafeSign to switch OpenSC off, which would cost the ePass2003 to whoever has both, OpenSC's configuration ignores the readers named "StarSign" (`ignored_readers`), so it never opens the token; a G+D card in an ordinary reader still needs OpenSC switched off.
43. **A driver without a token hid the other drivers' tokens.** With OpenSC on and no card in it, the GD Burti's token vanished for every app (JSignPdf, Firefox, `p11-kit list-tokens` in a sandbox, which listed only the trust store), while Tessera itself saw it; and taking a token out made the window say the system's p11-kit server was off, while signing with the other token still worked. The cause is in p11-kit's RPC, still in its current code: the server sends a NULL array for an empty slot list, and the client answers `C_GetSlotList(CK_TRUE, buffer, &0)` with `CKR_BUFFER_TOO_SMALL`. The system's p11-kit server walks its modules in order with `p11_kit_iter`, which stops at the first error, so every module after an empty one of Tessera's went missing for new connections. p11-kit orders modules by their `priority:` (highest first, 0 when unset; its trust module has 1), then by name: Tessera now writes `priority: -1` in the module file of each driver without a token, and drops it when the driver has one, so the empty ones come last and cut nothing off. The same fix ends the false "server off" warning; its text now says only that what answers does not list Tessera's tokens.
44. **JSignPdf signs.** After that, JSignPdf still said "No private key was found": Java's debug log (`-Djava.security.debug=sunpkcs11,pkcs11keystore`) showed SunPKCS11 opening the right slot (`slotListIndex`) at startup, but the signature using a JKS keystore. JSignPdf's **Keystore type** stays at its default, JKS, until PKCS11 is chosen, and the PIN goes in **Keystore password**. **Set up** now also writes `keystore.type=PKCS11` in JSignPdf's `config.properties`. With that, JSignPdf signed with the GD Burti.
45. **Master PDF Editor, set up by Tessera.** A user's settings file showed the key the "PKCS#11 provider" field writes, `pkcs11-helper-provider` under `[General]`; **Set up** now writes it, and step 2 is no longer by hand.
46. **Restart Tessera.** Thunderbird's profile, made after Tessera started, stayed unseen until Tessera was closed and opened again: a sandbox mounts a granted folder only if it exists at startup. The menu now has **Restart Tessera**, and an app's step 2 offers it when the app is installed and its folder is not seen; it starts a new instance through the Flatpak portal (`Spawn`), mounted afresh, which waits for the old one to leave the session bus. The refresh button now also checks, at once, each app's steps and what the apps see through the system's server.
47. **Each extension listed twice when uninstalling.** `flatpak uninstall` of Tessera listed each driver extension twice, the second time ending in "not installed" (`[✗]`), though everything was removed. A bug of Flatpak's, reproduced without Tessera (a made-up app with two extensions, on Flatpak 1.14.6): to find what an extension point with `subdirectories` takes along, `local_match_prefix` (`common/flatpak-dir.c`) adds both the repository's refs, which keep the remote's name in front (`remote:runtime/…`), and the installed ones, without it; they compare as different, and the transaction gets two operations for one extension. Harmless; the FAQ says so.
48. **JSignPdf, one token at a time.** With the GD Burti and SerproID plugged in, JSignPdf showed only the GD Burti's certificate: Java's SunPKCS11 opens one slot, and **Set up** wrote the first one holding a token of Tessera's. JSignPdf's row now has a list of Tessera's tokens when there is more than one; **Set up** writes the slot of the one picked and notes it in `pkcs11.cfg` (two comments, which SunPKCS11 skips), and the row asks for **Set up** again when the token picked is not the one the file was written for.
49. **Evolution's icon.** On CachyOS with KDE, Evolution's Flatpak row had a grey envelope: it was the generic icon, because Evolution was not installed as a Flatpak (the window lists every supported app, installed or not, and keeps it that way, so all the rows look alike). On the way, Tessera started to pass over theme icons that are only monochrome or 16 to 24 px (that desktop's theme has Evolution's at 16 px only), and to read an installed Flatpak's icon from the app's own files (`<installation>/app/<id>/current/active/export/share/icons/hicolor`) before Flathub's AppStream copy.
